主线、心愿、支线等「动作目标」都用同一套判定 `wishMatches()`：给出「哪种动作算一次」，再列出哪些真实地点动作也算。所以真实地点能否完成某个目标，只看数据里有没有写 `venue`，不需要写特例代码。

问题：

1. **成就不发奖励，也不进存档。** 达成以后没有反馈，「拿到过」也会丢，比如卖掉房子以后「有房一族」就不亮了。
2. **主线只有 2 章。** 写完以后，除了每日心愿，就没有带叙事的目标了。NPC 好感剧情是被动触发的，没有「去做点什么」的引导。
3. **任务分散在今天页、成长页、社交页三处。** 没有一个地方能看到「我现在有哪些事可以做」。
4. **只有片区称号。** 称号只能看，不能挑一个显示出来。

### 2.1 主线

- 【现状】2 章，不改。
- 【v28 已做】判定代码抽到 `core/steps.ts`，主线和支线共用。目标判定新增 6 种状态条件，主线也能用：指定 NPC 好感、主线章数、某条支线已完成、打卡数、图鉴数、鱼种数。主线行为不变，现有主线测试全过。
- 【提议】第三章「把日子过成自己的」：目标写成状态条件，例如「完成任意 2 条支线」（`{ t: 'side' }` 的计数版）、「有一份职业做到第二级」。真实地点路线（GPS 分支）开放后，可以加 `{ t: 'trail', id }` 状态目标，但只能作为「也算」的那一种做法，不能是唯一做法（见第 4 节）。

### 2.2 支线【v28 已做】

**数据**（`data/quests.ts`）：每条支线包含

- `unlock`：解锁条件（状态条件数组）；
- `steps`：目标，写法和主线一样，可以多加 `at`（限定游戏地点）；
- `reward`：奖励；
- `hint`、`intro`、`outro`：解锁提示、开场和结尾文案。

**规则**（`core/quests.ts`）：

1. 解锁条件全部成立时，支线自动接下，不用去找人点「接任务」。手机上少一步，不会漏接。
2. 只有动作之前就已经解锁的支线，才算这次动作。如果这次动作刚让支线解锁（比如这次帮忙把好感带到 30），这次帮忙不算第一步。和主线「刚进下一章不把同一个动作再算一次」是同一条规矩。
3. 状态目标做到就记下，之后丢了也不收回（同主线）。
4. 几条支线可以同时进行，互不影响。
5. 做完立即发奖，记进 `side.done`。之后同样的事再做多少遍也不再推进、不再发奖。
6. 解锁条件后来又不成立了（比如好感掉回 30 以下）：进度保留，暂停推进，重新成立后接着做。

### 2.3 每日 / 每周

- 【现状】心愿、每日奖励、全服周目标不改。
- 【v28 已做】心愿判定加了两个可选写法，现有心愿没用到，行为不变：
  - `{ t: 'npc', npc }`：只算和指定 NPC 的互动；
  - `{ t: 'fish' }`：钓到了鱼才算，空军不算。
- 【提议】**个人周目标**：每个现实周从心愿池里挑 3 个「做 N 次」的目标，做完给小额现金。它和全服周目标分开：全服目标靠一起凑，个人目标保证一个人玩也有每周目标。存档字段可以照 `weekly` 的形状加一个 `myWeek`。

### 2.4 收集

- 【现状】图鉴、鱼获、相册、收藏册、摄影任务、见闻录都不改。
- 【v28 已做】任务卡里汇总这几项的进度：
  - 摄影任务的下一张提示；
  - 图鉴每组 x/y；
  - 鱼种数；
  - 还差几个片区称号。

### 2.5 成就【v28 已做】

- 达成仍然按存档现算。新增「领取」：成就格里达成未领的成就显示按钮，点了发一个 `{ t: 'claim', id }` 动作。服务端用 `applyAction` 核对「现在达成」和「没领过」，两条都满足才发，同时把成就 id 记进 `achClaimed`。
- 领过就是领过：之后条件丢了（卖了房），格子仍显示「已领」，称号也不收回。
- 奖励写在成就数据里：不写的按 `ACH_DEFAULT_REWARD`（声望 +1）；`title: true` 另给一个和成就同名的称号。
- 达成时的提示改成「达成成就：××（去成长页领奖）」。

## 3. 奖励类型

| 类型 | 用在哪里 | 约束 |
| --- | --- | --- |
| 现金 | 主线、支线、周目标、每日奖励 | 一次性，量级不超过一两天正常收入。经济分支（`claude/earth-economy`）的收入来源表要加上「支线 $150」 |
| 声望 | 几乎所有层 | **声望是等级的唯一来源**（升级门槛 0/10/25/50/90…），也是高级职位的门槛。新增来源要进预算表（第 8 节）。成就奖励要手动领，现在的模拟策略不领，所以模拟测不到这部分 |
| 心情 | 主线、支线、心愿 | 用已有的 `wish-done` 等心情状态，不新增 |
| NPC 好感 | 支线 | 只给发支线的那位 NPC，+5 一次，钳在 100 |
| 称号【v28 已做】 | 片区、成就、支线 | 纯外观，不影响任何检定和数值。`core/titles.ts` 汇总 3 种来源：`area.*`、`ach.*`、`side.*`。戴一个，显示在今天页名牌上（替换等级称号的位置），成长页「称号」卡可戴可摘 |
| 外观【提议】 | 成就、支线、节日 | 头像框或名牌底色。和称号一样只是外观；需要在在线频道的广播里加一个字段，同地点的其他玩家才看得到。广播有大小上限，要和 `claude/earth-live-social` 一起定 |

称号显示给别人看（在线频道、排行榜、留言板）属于【提议】，要和联机分支一起改广播格式。第一版只有自己看得到。

## 4. 和真实地点打卡、GPS 的关系

原则：**真实地点「也算」，但从不是唯一做法。** 这和 GPS 路线分支（`claude/earth-gps-route`，`gps-route-design.md`）的原则一致。

玩家里有拒绝定位的、不在珀斯或阿德莱德的、只在宿舍玩的。所以：

1. 任何主线、支线、心愿目标，都必须有不用定位就能完成的做法。数据里用 `venue: [...]` 列出「在真实场所做也算」，用 `act` 写游戏里的做法。两种都写，测试检查 `venue` 里的动作存在。
2. 带 `at`（限定游戏地点）的目标不接受真实地点动作。真实场所的坐标和游戏地点不是一回事：人在珀斯的真实超市，不等于游戏里在弗里曼特尔。这一条有测试，变异检查也覆盖了。
3. 真实地点动作的冷却、每日上限、上班时长，仍由 `venue` 规则管（`core/venues.ts`）。支线只读「这个动作成功了没有」，不另外给真实地点加奖励。
4. 伪造定位：现状是服务端信任客户端上报的坐标。所以只靠定位才能拿的奖励要「一次性、量小」：打卡首次声望、路线奖励都是这样。支线的真实地点做法和游戏内做法奖励一样，伪造定位拿不到更多。
5. 【提议】GPS 路线合并后，主线、支线可以用状态条件 `{ t: 'trail', id }`（走完某条路线），但只能和其他条件「任选其一」，不能是唯一条件。要实现这一点，状态条件需要支持「任一成立」，第一版的 `unlock` 是「全部成立」。

## 5. 和 NPC 好感剧情的关系

| | NPC 好感剧情【现状】 | 支线【v28】 |
| --- | --- | --- |
| 触发 | 好感跨过门槛（10/30/60/90）时被动触发 | 好感 ≥30 时解锁，需要玩家主动去做 |
| 内容 | 一段文字 + 效果 | 几个目标 + 结尾文字 + 奖励 |
| 奖励 | 心情、现金、能力、声望 | 现金、声望、好感 +5、称号 |

设计上的分工：好感剧情是「关系到了，发生了什么」，支线是「关系到了，你可以为 TA 做什么」。

- 支线解锁门槛 30 和好感剧情的 30 档同时到。玩家先看到「打烊后的闲聊」这类剧情，再在任务卡里看到这位 NPC 的支线。
- 支线结尾加好感 +5，可能把关系推过下一个门槛（比如从 57 到 62）。这时 60 档剧情会在下一次和 TA 互动时触发（现有规则：剧情在互动结算里判断），不会在支线结算里重复触发，也不会漏。
- 支线只给发支线的那位 NPC 加好感，不给联动的另一位加。NPC 联动的触发条件不变。
- 【提议】每位 NPC 一条支线链：30 档一条，60 档一条（前置 `{ t: 'side', id }`），90 档一条。第一版只写了 3 位 NPC 的 30 档，验证机制。剩下 14 位 NPC 的支线文案量大，按仓库分工，应该先出模板，再分批写。

## 6. 防重复领取、跨设备同步

| 风险 | 机制 | 在哪 |
| --- | --- | --- |
| 客户端自己改存档领奖 | 存档只能由服务端 `applyAction` 改；领奖是普通动作，服务端用自己存的存档核对达成、未领 | `core/actions.ts`、`core/quests.ts` |
| 同一次点击重交（断网重试） | 动作编号 `op` 去重：同一个编号只执行一次，重交返回上次结果和已落盘存档 | `server/world.ts` 现有机制 |
| 两台设备同时领 | 版本号 `rev` 必须等于服务端当前版本，落后的返回 409 和最新存档，不执行 | 同上 |
| 领过以后条件又成立 | `achClaimed`、`side.done` 是只增不减的列表，和存档同一次写入 | `PlayerState` |
| 伪造存档字段 | `sanitizeState` 只留认识的成就 id、支线 id；进度钳到目标次数；做完的支线不留进度；称号必须在这份存档已拿到的称号里，否则清成 `''` | `core/character.ts` |
| 伪造动作参数 | `parseAction`：`claim` 的 id 只收 `[a-z0-9-]`；`title` 的 id 只收 `area.*` / `ach.*` / `side.*` 或空串 | `core/actions.ts` |
| 支线结算两次 | 结算在 `applyAction` 里，和动作同一份新存档；做完的支线跳过 | `settleSide` |

第一版的测试覆盖了上面每一行。服务端测试走真实 `EarthWorld.fetch`：

- 没达成时被拒；
- 达成后领一次；
- 同一个 `op` 重交只认一次；
- 旧版本号返回 409；
- 再领被拒；
- 落盘的声望只加了一次；
- 存档里伪造的称号在读取时被清掉。

### 变异检查

人为改坏 20 处关键判断，每处单独跑任务、主线和心愿的测试，20 处全部让测试失败。

第一轮有 1 处没被发现：「做完的支线再发奖」。原因是另一条规则（动作只算进动作前已解锁、未完成的支线）挡住了动作目标；但只有状态目标的支线，靠这条规则挡不住，会重复发奖。为此给 `settleSide` 加了可选的支线表参数，补了「只有状态目标的支线只发一次」的测试。

脚本放在会话临时目录，没有提交。改动清单：

- 成就：已领还能领、没达成也能领；
- 支线：解锁那次动作也算、做完再发、不加好感、好感不钳制；
- 称号：没拿到也能戴；
- 判定：限定地点、NPC 解锁、章节解锁、指定 NPC、空军算钓到这几条失效；
- 存档清洗：不核对称号、不钳进度、做完的留进度、不认识的成就 id 留下；
- 动作：不结算支线、领奖不核对、称号 id 不校验格式；
- 主线：新章重复计同一个动作。
