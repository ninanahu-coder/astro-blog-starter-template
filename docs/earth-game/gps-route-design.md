# 主要路线：真实 GPS 走路线、沿途触发事件（v22）

本文是「地球人生」主要路线（代码里叫 trail，实地路线）的设计方案和第一版实现说明。代码在 `src/game/core/trails.ts`、`src/game/data/trails.ts`、`src/game/data/trail-events.ts`，测试在 `tests/earth/trails.test.ts`。所有数值都**待平衡**，交给 Codex 分析。

## 1. 「主要路线」是什么

游戏里已经有两层真实地理：

| 层 | 尺度 | 现有玩法 |
| --- | --- | --- |
| 游戏地点（`GameLocation`） | 城市，半径 6–40 km | `gpsCheckIn`：真实定位落在半径内就「抵达」这个城市 |
| 真实地点（`Venue`、`Poi`） | 一家店、一个公园，半径 50–400 m | 「附近」页：人在店里才能吃饭、训练、打卡上班 |

两层之间缺一样东西：**把几个真实地点按顺序串起来、跟着故事走的一条线**。主要路线就是这一层：

- 每条路线属于一个游戏地点（珀斯、弗里曼特尔、阿德莱德……），由 3–5 个**站**组成，按顺序走；
- 站只引用已有的真实地点：`wa.pois.json` 的种子打卡点或 `*.venues.json` 里 OSM 采集的地点。路线数据里抄一份名字和坐标，测试逐条核对和来源一致，不引入新坐标；
- 路线**按主线章节解锁**：第 1 章「落地珀斯的头一周」开放市中心步行、弗里曼特尔老城、阿德莱德棋盘城这几条「认路」路线；第 2 章「找到稳定工作和住处」开放国王公园。玩家走的是和故事同一阶段的真实街区；
- 不做「记录玩家每天真实走过的路」。那样需要持续定位和轨迹存储，耗电、隐私成本都高，而且留学生每天的真实路线（家—学校—打工）游戏没法预先写内容。

一句话：**主线故事告诉你这一章在做什么，主要路线让你本人去这一章的街区走一圈。**

### 为什么是可选的

玩家里有拒绝定位的、不在珀斯或阿德莱德的、只在宿舍里玩的。主线章节的目标**不依赖**路线：路线是同一章节的「实地版」，走完有额外奖励和专属事件，不走也能把故事推完。将来如果某章要把路线写成目标，用 `story.ts` 的状态目标加一个 `{ t: 'trail', id }` 即可（第一版没有加，避免把不能出门的玩家卡住）。

## 2. GPS 怎么推进路线

玩家在「出行 · 附近」页看到本章路线和下一站，点「📍 我到了 / 沿途看看」时取一次高精度定位，发动作 `{ t: 'trail', lat, lon, acc }`。服务端用 `applyAction → trailStep()` 结算。一次动作只做下面一件事：

1. **到站**：定位离下一站 ≤ 站半径（默认 80 m）+ min(精度, 50 m) → 这一站算到达：结算这一站的小收获（`fx`），有到站事件就挂上（`pending`），走完最后一站发路线奖励；
2. **沿途**：还没到下一站，但定位落在「上一站 → 下一站」的走廊里（离线段 ≤ 150 m，沿线段方向走了 20%–85%），而且这一段的沿途事件还没出过 → 触发这一段的沿途事件。每段最多一次；没赶上也不影响到站；
3. 都不是：返回「离下一站还有 N 米」，不改存档。

站必须按顺序到。玩家可以同时有好几条路线在进行（不同城市），一次动作只推进第一条命中的。

沿途判定用的是线段投影（`legProgress`，在局部等距平面上算，几公里内误差可以忽略），不需要路网数据，也不需要连续定位：玩家自己想起来点一下就行。

## 3. 防作弊

坐标来自手机，可以伪造。服务端能做的是让伪造**不划算**，而不是不可能：

| 检查 | 规则 | 代码 |
| --- | --- | --- |
| 精度太差 | 误差 > 150 m 不受理（沿用真实地点的 `FIX_RULES.maxAccuracyM`） | `fixProblem` |
| 精度可疑 | 误差 < 1 m 不受理：真机定位不会报 0 米，开发者工具和部分模拟定位软件会 | `TRAIL_RULES.minAccuracyM` |
| 瞬移 | 和存档里上一次定位比，推算速度 > 200 km/h（且相距 > 2 km）不受理（沿用 `fixProblem`）。每次成功的路线动作都更新 `fix` | `fixProblem` |
| 走得太快 | 站和站之间按**直线距离 ÷ 两次服务端时间**算速度，> 25 km/h 不受理（步行、跑步、骑车都够，开车刷站不行）；沿途事件同样按「上一站 → 这次定位」检查 | `TRAIL_RULES.maxKmh` |
| 时间 | 一律用服务端时间 `now`，客户端时间不参与 | `applyAction(…, now)` |
| 离线补交 | 路线动作不能排队补交（`queueable` 默认拒绝），旧坐标不会在几小时后被当成现在 | `ui/queue.ts` |
| 重复刷 | 每站只能到一次，每段沿途事件只出一次，路线奖励只发一次 | `state.trails` |

做不到的：网页拿不到系统的「模拟定位」标记，一个慢慢沿路线「走」假坐标的人仍然能通过。对策是把路线收益压在「一次性、量小」：整条路线的奖励和一两天正常游戏的收入同级，没有可重复刷的部分。

已知缺口（不在本版范围）：现有的 `gps` 抵达动作不带精度、也不查速度，可以直接把游戏位置瞬移到任何城市。路线动作要求游戏位置已经在路线所在城市，所以这个缺口会被继承到「能不能开始走路线」，但不影响逐站的速度检查。建议另开任务给 `gps` 加上 `acc` 和 `fixProblem`。

## 4. 隐私

- **不存轨迹**：存档只记每条路线到了第几站、这一段沿途事件出没出、到上一站的服务端时间（`trails: { [id]: { at, leg, t } }`），没有坐标；
- 唯一的坐标是已有的 `fix`：最近一次定位，保留 3 位小数（约 100 米），用于下一次的速度检查。路线动作和真实地点动作共用它，不多存；
- 服务端不记日志、不广播坐标；日志里只写「到了国王公园」这类站名（站名是公开地点）；
- 客户端定位只在内存里（`nearFix`），不写 `localStorage`，不进离线队列；
- 只在玩家点按钮时定位一次（`getCurrentPosition`），不用 `watchPosition`，不在后台定位。

## 5. 离线和定位权限被拒

| 情况 | 表现 |
| --- | --- |
| 定位权限被拒 / 设备不支持 | 路线卡照常显示站名、顺序和进度，按钮点了提示「无法获取定位」；主线故事、其他玩法都不受影响 |
| 离线 | 路线动作要服务端时间，离线时提示「要联网才能做」，不排队（见上表） |
| 不在路线所在城市 | 提示先用真实定位抵达这个城市（和真实地点动作一致：页面会先自动发一次 `gps` 抵达） |
| 存档里的进度坏了 | `sanitizeState` 只留已知路线 id，站数钳到 0..站数，时间不能晚于服务端现在 |

## 6. 和现有代码的关系

- **`gpsCheckIn`**：城市一级的抵达，不变。路线是城市内部的一层；路线动作要求游戏位置已经在这座城市（`state.loc === trail.loc`），否则返回提示，页面先发 `gps` 再发 `trail`；
- **`venues.ts`**：复用 `fixProblem`（精度 + 瞬移）和 `fix` 字段；站半径的定位误差容忍沿用 `FIX_RULES.accuracySlackM`；
- **`story.ts`**：路线用 `chapter`（章序号）挂在主线上，`state.story.ch ≥ chapter` 才开放。已经写完的章节对应的路线一直开放；
- **事件**：到站和沿途事件放在 `data/trail-events.ts`，`weight: 0`（不进到达、真实地点的普通抽取），由路线数据按 id 指定；合进 `EVENTS`，所以 `resolveEvent`、存档校验、界面弹窗都不用改；
- **心愿**：路线动作不算任何心愿（`wishMatches` 不认识 `trail`）。

## 7. 数据格式

```ts
// data/trails.ts
interface TrailStop {
  ref: string;      // wa.pois.json / *.venues.json 里的 id
  name: string;     // 抄来源里的名字
  lat: number; lon: number; // 抄来源里的坐标（测试逐条核对）
  text: string;     // 到站时的描写
  fx?: Effect;      // 到站的小收获（待平衡）
  event?: string;   // 到站事件 id（trail-events.ts）
  along?: string;   // 从上一站走到这一站途中的事件 id
  radiusM?: number; // 默认 TRAIL_RULES.stopRadiusM
}
interface TrailDef { id; title; loc; chapter; intro; outro; stops: TrailStop[]; reward: Effect }
```

## 8. 数值（全部待平衡）

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `stopRadiusM` | 80 | 到站半径（再加 min(精度, 50)） |
| `corridorM` | 150 | 沿途走廊半宽 |
| `alongFrom` / `alongTo` | 0.2 / 0.85 | 沿途事件要在这段路的这个区间里 |
| `maxKmh` | 25 | 站与站之间的最高平均速度 |
| `minAccuracyM` | 1 | 精度小于它视为异常 |
| `stopMinutes` | 20 | 到站花的游戏时间 |
| 每站 `fx` | 娱乐 +4~8 等 | 见数据 |
| 路线奖励 | $30–60、声望 +2~3、心情「心愿达成」 | 见数据 |

数值模拟（`npm run earth:sim`）里的机器人不走真实定位，所以这一版对模拟结果没有影响；平衡上要看的是「一个真实玩家每周走一两条路线」带来的额外收入和声望，交给 Codex 估算。

## 10. 第一版的验证

- `tests/earth/trails.test.ts` 13 个用例：数据逐站核对来源（id、名字、坐标、所在城市、来源只能是 seed / osm / wikidata）、到站顺序、到站半径和误差容忍上限、精度不够 / 精度可疑 / 瞬移 / 站间太快、沿途走廊和每段一次、章节开放、换城市提示、晕倒不算站、动作协议和离线排队、存档校验、经服务端入口落盘；
- 变异检查：逐个改坏 18 处实现（去掉速度检查、去掉精度检查、不查走廊、不按章节开放、坐标不取整、修改入参、存档不钳站数、路线动作可排队、站坐标抄错等），每一处都让上面的测试失败；
- 数值模拟 `npm run earth:sim -- --days=180 --runs=100` 改动前后输出逐字相同：机器人不走真实定位，路线事件 `weight: 0` 不进普通抽取，随机数序列不变；
- 首屏脚本约 393KB → 411KB（路线数据、事件文案、路线卡），`bundle.test.ts` 的上限从 400KB 提到 420KB；
- 路线事件的插图暂时借用相近的已有插图（清单里指向已有文件），`tools/earth/comfyui/prompts.mjs` 已写好专门的提示词，生成脚本按文件是否存在判断，跑一次就会换成专门的图。
